# 03. 強み・こだわり

スライドの「推しポイント」や、質疑で聞かれたときの答えに使ってください。

## 1. 「知識」ではなく「判断」を体験する

- 営業研修の座学で学ぶ BANT・TCO・責任共有モデルなどを、**実際に選ぶ場面**に置いた
- 同じ顧客でも、面談相手・予算・競合・時期で正解が変わる（216 通り）。暗記では勝てない
- **聞かないと分からない**：予算・競合・時期は、質問や調査をして初めて案件シートに書き込まれる。「ヒアリングの価値」をゲームの仕組みそのもので伝える

## 2. 「高いサービスを並べても受注できない」採点

- 課題に必要な部品を揃えることを評価し、関係の薄いサービスは減点。予算感を超えると経済性が下がる
- 値引きは受注しやすくなるが、年間利用見込み（売上）が下がる。PoC の段階で長期契約を求めると減点
- 競合がいるほど、受注に必要な点数が上がる
- バランスを数値で確認済み：最適な判断は 96〜100 点、ランダムに選ぶと受注率は約 8%

## 3. 結果から「なぜ」が分かる

- 案件クローズ報告書に、工程ごとのフィードバックを ○ △ × で表示（例：「サーバーが古い」は症状の 1 つです、など）
- 「模範的な進め方」を同じ条件で表示し、自分の判断と並べて比べられる
- 「営業の基本」ページで、役割分担・ヒアリングの型・費用の考え方・反論への答え方・クロージングをまとめた

## 4. AI っぽくない、業務の道具らしい見た目

- 営業部の「案件シート」「商談記録票」をモチーフにした紙と罫線のデザイン。グラデーション・影・角丸カード・絵文字・アイコンの多用を避けた
- 商談の進み具合は CRM の「パイプライン」風の矢羽根、面談相手は「名刺」、結果は朱色の「受注」印を押した報告書で表示
- 数字は等幅フォント、本文は UD フォント（BIZ UDPGothic）で読みやすさを優先
- スマートフォンでも操作できる（イベント中に QR コードから参加してもらう想定）

## 5. 公平で信頼できる記録

- 採点エンジン（`shared/engine.ts`）をブラウザと Lambda で共有。保存時はサーバーが計算し直すため点数を改ざんできない
- 入力はすべてサーバーで検証。他の利用者の ID は API の応答に含めない
- ログインは「記録するときだけ」。体験・閲覧はログイン不要

## 6. イベント向けの「使い捨てやすさ」

- 常時起動のサーバーなし（EC2・NAT・ALB・RDS・API Gateway を使わない）。WAF も外して固定費ほぼ 0
- cdkd で作成・削除を短時間で行える。記録は 90 日で自動削除
- `-c destroyData=true` で、削除時に記録とユーザーもまとめて消せる

## 7. AI-DLC で「決めたこと」が残っている

- 要件（FR / NFR）・設計判断（ADR：WAF を使わない理由など）・ユニット分割・テスト結果を [aidlc-docs/](../aidlc-docs/README.md) に記録
- AI-DLC のハーネス（`.claude/`）を同梱。新しいセッションで `/aidlc feature ...` から続きを開発できる

## 想定質問と答え

| 質問 | 答え |
| --- | --- |
| 採点は AWS 公式の基準？ | いいえ。一般的な営業の考え方をもとにした学習用の簡略モデルです。画面とフッターにも明記しています |
| 生成 AI で会話するのでは？ | あえて使っていません。全員が同じ条件で比べられ、採点の理由を説明でき、費用もかからないためです。将来、反論への自由回答を Bedrock で評価する拡張は考えられます |
| WAF なしで大丈夫？ | イベント期間だけの公開で、OAC・ログイン必須の保存・サーバー側の再計算・キャッシュで守っています。常設するなら WAF を足します |
| cdkd を本番で使える？ | cdkd は開発・検証用途向けと案内されています。今回のような短期のイベント環境や検証環境に向いています |
