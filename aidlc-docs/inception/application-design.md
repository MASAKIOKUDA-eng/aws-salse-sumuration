# Application Design / NFR Design

## 構成

```
 ブラウザ ───────────────▶ Cognito マネージドログイン … 登録・ログイン（認可コード + PKCE）
   │ HTTPS
   ▼
 CloudFront (PriceClass 200 / HTTP2+3 / 圧縮)   ※ WAF なし（ADR-4）
   ├─ /*      → S3 バケット（非公開, OAC）       … 静的フロントエンド + config.json
   └─ /api/*  → Lambda Function URL（IAM, OAC）… API (Node.js 22 / arm64)、アクセストークン検証
                     │
                     ▼
               DynamoDB（オンデマンド, TTL 90 日） … 商談の記録
```

| リソース | 選定理由（コスト重視） |
| --- | --- |
| CloudFront | 無料利用枠が大きい。API も同一オリジンで配信し CORS 不要 |
| S3 | 静的ファイルのみ |
| Lambda Function URL | API Gateway の料金が不要。arm64・256MB |
| DynamoDB オンデマンド | アイドル時の課金なし。GSI なしの単一テーブル設計 |
| CloudWatch Logs | 保持期間 1 週間 |
| Cognito（Essentials） | 月 1 万 MAU まで無料。マネージドログイン画面を使う |

## API

| メソッド | パス | 認証 | キャッシュ | 内容 |
| --- | --- | --- | --- | --- |
| GET | `/api/deals?limit=` | 不要 | 10 秒 | 最近の商談（最大 50 件） |
| POST | `/api/deals` | 必要 | なし | 記録。`{ playerName, seed, decisions }` を受け取り、サーバーで採点し直して保存 |
| GET | `/api/deals/{id}` | 不要 | 60 秒 | 記録の詳細 |
| GET | `/api/me/deals` | 必要 | no-store | 自分の記録 |
| GET | `/api/leaderboard` | 不要 | 30 秒 | 直近 300 件のうち点数上位 10 件 |

## データモデル（単一テーブル）

| pk | sk | 内容 |
| --- | --- | --- |
| `DEAL` | 時刻順 ID | 記録の本体（判断・結果・条件のシード・利用者 sub） |
| `USER#<sub>` | 同じ ID | 自分の記録用の要約（判断は含めない） |

2 件は TransactWrite で同時に書く。`expiresAt`（90 日後）で TTL 削除。

## 採点モデル（U1）

- 条件 = シナリオ（4）× 面談相手（3）× 予算感（3）× 競合（3）× 時期（2）= 216 通り。mulberry32 でシードから決める
- 合計 = 顧客理解 25% + 提案の適合 30% + 経済性 20% + 信頼構築 25%
- 受注確度 = 1 / (1 + exp(−(合計 − 閾値) / 6))。閾値は競合なし 64・既存 SIer 68・他社クラウド 72
- `bestDecisions()` は条件ごとに構成・進め方・費用・クロージングを全探索して模範解答を出す（画面表示とテストに使う）

## 設計判断

### ADR-1 参考リポジトリの構成を踏襲する

- **Context**：短期間で作り、cdkd の検証対象として「実案件に近い」構成にしたい。参考リポジトリで実績がある。
- **Decision**：CloudFront + S3 + Lambda Function URL（OAC）+ DynamoDB + Cognito、エンジン共有・サーバー再計算・ログ付きデプロイスクリプトを踏襲する。
- **Consequences**：認証（PKCE）・OAC の `x-amz-content-sha256`・`x-auth-token` ヘッダーなどの実装を再利用できる。
- **Alternatives Rejected**：API Gateway + Lambda（料金と構成要素が増える）、Amplify Hosting（cdkd の検証対象として CDK の素のリソースを使いたい）

### ADR-2 生成 AI を使わない、ルールベースの採点

- **Context**：営業ロールプレイは生成 AI と相性が良いが、イベントでは参加者同士で点数を比べたい。
- **Decision**：選択式の判断と、重みテーブルによる採点にする。フィードバックも判断ごとの定型文で返す。
- **Consequences**：同じ条件なら同じ点数になり、サーバー再計算で改ざんを防げる。採点理由を説明できる。会話の自由度はない。
- **Alternatives Rejected**：Bedrock による自由会話と採点（費用・ばらつき・プロンプトインジェクションへの対策が必要）

### ADR-3 「聞かないと分からない」条件

- **Context**：ヒアリングの価値を、説明ではなく仕組みで伝えたい。
- **Decision**：予算感・競合・時期は、対応する質問（予算・意思決定・時期）または調査（既存ベンダー）を選んだときだけ表示する。後の判断の重みはこれらの条件で変わる。
- **Consequences**：聞かなかった利用者は勘で決めることになり、結果のフィードバックで「何を聞くべきだったか」を示せる。

### ADR-4 WAF を使わない

- **Context**：参考リポジトリでは WAF（Web ACL + ルール 3 つ、約 8 USD/月 + リクエスト課金）を付けていた。本アプリはイベント期間だけの公開。
- **Decision**：WAF は作らない（スタックも持たない）。代わりに、OAC + IAM 認証で API の直接呼び出しを禁止／保存はログイン必須／入力検証とサーバー再計算／GET 応答の CloudFront キャッシュ／TTL による記録の自動削除、で守る。イベント後はスタックを削除する。
- **Consequences**：固定費がほぼ 0 になり、us-east-1 のスタックやリージョンをまたぐ参照が不要になるため、構成もデプロイも単純になる。大量アクセスによる Lambda・DynamoDB の課金リスクは残る（オンデマンドかつ GET はキャッシュされるため、イベント規模では軽微）。
- **Alternatives Rejected**：WAF を付ける（コストに見合わない）、Lambda の予約同時実行数で上限を設ける（新しいアカウントでは同時実行数の上限が低く、デプロイに失敗することがあるため見送り）

### ADR-5 トークンの受け渡しとクライアント ID（参考リポジトリの ADR-2・3 を継承）

- アクセストークンは独自ヘッダー `x-auth-token` で送る（OAC が `Authorization` を署名に使うため）
- Lambda はユーザープール ID とトークン種別で検証し、クライアント ID は検証しない（循環参照を避ける。このプールのクライアントは 1 つだけ）

### ADR-6 見た目：営業の帳票

- **Context**：「AI っぽい」見た目（紫のグラデーション、角丸カード、絵文字、光沢）を避けたい。
- **Decision**：紙の地色・墨の文字・罫線・朱の印。案件シート、名刺、CRM のパイプライン、案件クローズ報告書、○△× の評価記号など、営業の現場の道具を画面の部品にする。フォントは BIZ UDPGothic と IBM Plex Mono。
- **Consequences**：画像アセットなしで世界観を作れる。業務アプリに近い見た目になり、営業の参加者にもなじむ。
